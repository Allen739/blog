# How GPUs Actually Work: A Warehouse of Identical Tiny Workers

> A GPU is not a genius in a box.
> It is a huge room full of workers who can all do the same small thing very fast.
> The trick is not intelligence. The trick is repetition.

## The wrong mental model

People often imagine a GPU as a tiny brain. That is the wrong image.

A CPU is a generalist. It can follow many kinds of instructions, branch constantly, and adapt to whatever strange task shows up next.

A GPU is much less flexible and much more brutal. It is built around lots of nearly identical workers. Each worker is simple. The power comes from having many of them do the same step at the same time.

![CPU Chef vs GPU Workers kitchen cooking analogy.](/blog/gpu-internals/01-cpu-gpu-comparison.png)

The useful question is not, "How smart is the GPU?"

It is, "How many identical things can it do at once?"

## One big job becomes many small slips

When a GPU runs a kernel, it does not treat the whole problem as one giant mystery.

It slices the work into many tiny pieces. Each worker gets a slip with the same instruction, just on different data.

That is why GPUs are so good at rendering pixels, multiplying matrices, and training neural networks. The work is repetitive. The instruction is simple. The data changes.

![Slicing a big job into 32 thread slips for a warp.](/blog/gpu-internals/02-job-warps.png)

The point is not elegance.

The point is scale.

## The lockstep problem

GPU workers usually march in groups called warps. On NVIDIA hardware, a warp is 32 threads.

That sounds efficient until one worker hits a branch:

```text
if x > 0:
    do A
else:
    do B
```

If the threads in the same warp disagree, the GPU has to serialize the paths. Some threads do A, then the others do B. The group stops being perfectly aligned.

That is divergence, and it is expensive.

![Warp divergence: threads split into two paths, serialized.](/blog/gpu-internals/03-warp-divergence.svg)

This is why GPU code tends to prefer simple, predictable control flow.

Less branching usually means more throughput.

## The real trick is hiding waiting

Memory is slow.

Fetching data from far away takes time, and that time dominates chip execution if nothing else is ready to run.

The GPU response is not to wait. It is to switch.

While one warp is stalled on memory, the scheduler swaps in another warp that already has work ready to go. The chip stays busy by keeping a large queue of runnable work.

![Hiding memory latency by swapping in a ready warp.](/blog/gpu-internals/04-hide-latency.svg)

This is the central trick of GPU performance:

not less latency, but better hiding of latency.

## Memory is arranged by distance

Not all memory is equal.

Registers are tiny and private. Shared memory is small but close to a group of workers. Global memory is huge, but far away and expensive to touch.

The good GPU programmer keeps hot data as close as possible to the worker doing the computation.

![Memory hierarchy: registers, shared memory, and distant global memory.](/blog/gpu-internals/05-memory-hierarchy.svg)

If you keep walking across the warehouse for every ingredient, the machine slows down.

If you keep the ingredients near the workers, the machine flies.

## Why GPUs win

GPU-friendly workloads have one thing in common: lots of repeated, independent work.

That is true for rendering, simulation, image processing, and most modern machine learning.

The GPU is not winning because each worker is brilliant.

It is winning because the whole system is built to keep a wall of workers moving together:

![Parallel throughput: thousands of Xiaoheis laying the same brick simultaneously.](/blog/gpu-internals/06-parallel-throughput.svg)

That is the whole idea.

One big job.

Many small workers.

Very little waiting.
